# 断裂标签重建：以可见分离第一帧为锚点重算事件时刻

> 状态：设计稿，2026-10-18 起草于分支 `feat/evaluation-development`；2026-10-18 用户已裁决 D1、D2（详见第 2 节）。本文不改代码、不改数据、不提交。剩余待裁决项只有各闸门阈值（第 4 节）。

> 事实边界：第 1 节的窗口规则与字段来源为 2026-10-18 本机只读实测核对。用户目视抽查结论来自 2026-10-18 的口头判断。`video_0110` 的 3.5 s 偏差为推断，本文未复算。本机未跑推理，也未重跑标注。

## 1. 问题陈述

### 1.1 目视抽查推翻了现有标签的前提

用户在 2026-10-18 目视抽查标为「已断裂」的子视频。结论：首帧看不到可见断裂的样本比例高，且分散在多个来源，不集中在个别视频。该结论是定性判断，用户没有给出百分比。

「已断裂」的当前定义要求子视频首帧已经处于断裂之后。首帧看不见断裂，这条样本在视觉上就不成立。前期所有指标都建在这批标签上。前提一倒，指标数字不再指向模型能力。

### 1.2 偏差线索

标注用 ROI metadata 的 `event_time` 定断裂时刻。人工判读依据的是「可见断裂时刻」。`video_0110` 两者相差约 3.5 s（推断）。单条样本不足以说明偏差的分布与方向，可以当排查入口。

3.5 s 的偏差与窗口判据里的 0.5 s guard 不在同一量级（推断，比较对象为 1.2 节的两个数）。偏差落在 guard 吸收不了的区间内。

### 1.3 窗口规则与 guard 的判定机制

常量 `EVENT_GUARD_SECONDS = 0.5` 定义在 `pipeline/v3_candidate_plan.py:36`。判定函数是 `_state_for_interval(record, interval)`（`pipeline/v3_candidate_plan.py:301`），逐条规则如下。

| 判定结果 | 条件 | 出处 |
| --- | --- | --- |
| 未断裂 | 区间 `end` 不晚于 `event - 0.5` | `pipeline/v3_candidate_plan.py:312` |
| 已断裂 | 区间 `start` 不早于 `event + 0.5` | `pipeline/v3_candidate_plan.py:314` |
| 发生断裂 | `start < event < end` | `pipeline/v3_candidate_plan.py:316` |
| 无法判断 | 以上都不成立 | `pipeline/v3_candidate_plan.py:319` 附近 |

源级特例在 `pipeline/v3_candidate_plan.py:307`–`:308`：源视频未夹紧或异常时判「无法判断」；无极值断裂源判「未断裂」。事件时刻不可靠时同样判「无法判断」。

裁窗规则：断裂前窗口终点 `pre_end = max(0.0, event - EVENT_GUARD_SECONDS)`（`pipeline/v3_candidate_plan.py:627`），断裂后窗口起点 `post_start = min(duration, event + EVENT_GUARD_SECONDS)`（`:659`）。两侧窗口按 fps 对齐到帧边界，由 `_aligned_interval` 处理（`pipeline/v3_candidate_plan.py:280` 起）。

### 1.4 推论：`event_time` 偏早则「已断裂」窗口整体前移

（推断）若 `event_time` 系统性早于可见断裂时刻，「已断裂」窗口的起点 `event + 0.5` 就会落在真实断裂之前。裁出的子视频首帧自然看不到断裂，标签与画面不符。

（推断）用户观察到的「分散」与系统性偏早相容：偏差大小随来源的视频帧率、裂纹发展速度、原标注习惯变化，所以不会集中在个别视频。若该推论成立，修 33 条无用，`event_time` 本身要重算。

### 1.5 影响面：四档标签都要复核

`event_time` 参与四档标签的每一档判定，见 1.3 节的表。`event_time` 不可靠的样本会整体落入「无法判断」，这一档的规模同样受事件时刻影响。

当前规模：`data-v4.1-r2` 共 1,678 条候选、85 个来源（`docs/project-todo.md:50`、`docs/project-todo.md:62`）。Fold0 validation 为 425 条，其中「已断裂」33 条（`docs/design-facts.md:69` 记载的 R1 旧口径结果）。训练池「已断裂」占 15.00%（DF-010）。

复核范围覆盖全部 1,678 条候选。只修 33 条会把「未断裂」与「发生断裂」的错标留在数据里，下一轮训练与评测继续带病。

## 2. 用户裁决项（D1、D2 已于 2026-10-18 裁决）

两项已于 2026-10-18 由用户裁决，结论见 2.1 / 2.2。下文各小节保留裁决前的原始问题、字段来源与选项对照，作为裁决依据的记录，不删。

### 2.1 D1 `event_time` 的语义

**状态：已裁决（2026-10-18）**

**裁决结论**：`event_time` 的语义定为「**可见分离第一帧**」的时间（即 D2 锚点），对应原选项 B 一侧（「完全分离」的视觉可判版本）。

**历史列不覆盖**：数据表新增 `visible_separation_time` 列承载该值；原 `断裂时间点` 列**原样保留、不改写、不换算**。保留目的是（a）统计新旧锚点的偏差分布与方向；（b）保留可追溯的原始标注输入。

保留理由三条：

1. **视觉可判性**：只有视觉可判的量才能作为视觉模型的标签与被评测对象；锚在物理裂纹起始（视觉不可判）会让模型永远无法判对，任何 recall 都测不出能力差异，评测因此失去意义。
2. **与用户原始定义一致**：用户给出的样本判读依据就是「画面里能看见分离」，锚点回到同一口径才与人工判读自洽。
3. **可被独立复核**：该锚点既能由标注者逐帧独立标定（可做一致性检验），也能由确定性检测规则独立复现（同一输入重复运行结果相同），因此可建金标准、可做闸门校验。

以下保留裁决前的原始问题、字段来源与选项对照，作为裁决依据的记录，不删。D1 已裁决，「不定会怎样」一段转为历史记录。

**问题**：`event_time` 指「裂纹起始时刻」还是「完全分离时刻」？

**字段来源（已实测核对）**：`pipeline/source_bootstrap.py:293` 从源表列 `断裂时间点` 解析，解析函数 `_parse_event_time` 在 `pipeline/source_bootstrap.py:202`。`:296`–`:297` 由 `event_time * fps` 反推 `event_frame`。`:319` 写入 `event_time_reliable`。下游时间轴度量见 `finetune/validation/task_metrics.py:143`（`_target_event_time`）。

**原始定义的登记位置**：源表列名与数据来源文档。仓库内未找到该列的口径说明（待核实，需向数据提供方或源表文档确认）。

**为什么必须先定**：语义决定自动检测要检测什么。「起始」与「完全分离」是两个不同的视觉事件，对应两套检测算法与两套金标准。

| 选择 | 后果 |
| --- | --- |
| A「裂纹起始时刻」 | 与「首帧是否已断裂」的视觉判据天然不一致。要让标签可用，必须改标签锚点；而物理起始在画面上不可判（见 D2） |
| B「完全分离时刻」 | 与视觉判据一致。现有 `event_time` 与可见断裂时刻存在偏差，说明它当前不满足此定义，必须重算 |

**不定会怎样（历史记录）**：无法判断该保留还是替换 `event_time`。自动检测的目标事件未定，第 3 节第 2 阶段的算法选型、金标准标注对象、第 4 节闸门的第一条判据全部悬空。D1 已于 2026-10-18 裁决，本段仅作裁决前状态记录。

**问题**：标签锚在「可见分离第一帧」（视觉可判），还是锚在「物理事件起始」（视觉不可判）？

| 1 金标准建立 | 取 N=60 条，跨不少于 10 个 `source_video`，每个来源不少于 3 条，覆盖四档，人工逐帧标出「第一帧可见分离」时刻 | 抽帧 `[需训练机]`；标注 `[本机可做]`（用本机已有帧图） | 同一人隔日复标一致率 ≥90%；多标者另报 Cohen's κ（阈值待用户定） | `golden/visible_separation.jsonl`（仓库内当前不存在，待建立） |

### 3.1 第 1 阶段：金标准建立

金标准是后续一切的对照物，样本选取要能支撑分档判断。D2 已裁决锚点为「可见分离第一帧」，本节据此把第 1 阶段写成可直接执行的清单，按顺序执行，不得跳步。

1. **抽样设计**：共 60 条；跨不少于 10 个 `source_video`；**每个来源不少于 3 条**；四档（未断裂 / 发生断裂 / 已断裂 / 临界未断裂）全覆盖且每档不少于 3 条。若实测某档在 1,678 条候选中的存量不足该下限，按实测存量取全量，并在清单里注明实际条数与来源。
2. **抽样来源与选择规则**：抽样池 = `data-v4.1-r2` 的 1,678 条候选；按 `source_video` × `clip_state` **分层随机**抽取，固定随机种子，种子值随产物落盘，抽样脚本可复跑且同种子结果一致。**禁止「先目视过一遍再挑」与人工择优**：只挑分离清晰的样本会系统性高估检测精度、低估误差，因此选择规则必须在看帧之前固定并落盘。抽样脚本的产物记录 `candidate_id` 清单与种子。
3. **标注单位**：**逐帧**。帧率必须从实际帧序列/源视频元数据**现场实测**（如 `cv2.CAP_PROP_FPS` 或等价手段），**不得假定 25fps**；实测 fps 随每条样本落盘，`visible_separation_time = frame_index / fps` 由脚本计算，不手算。
4. **标注输出格式**：JSONL，每条一对象，字段固定为以下九个，不多不少：
   - `candidate_id`：候选在 `data-v4.1-r2` 中的标识，与抽样清单一一对应。
   - `source_video`：来源视频标识，用于来源分布核对。
   - `fps`：该样本现场实测帧率，必须大于 0。
   - `visible_separation_frame`：可见分离第一帧的帧号，整数，落在该样本帧数范围内。
   - `visible_separation_time`：`frame_index / fps`，由脚本计算，不手算。
   - `confidence`：标注者对该判断的置信度。
   - `annotator`：标注者标识，用于一致性检验与责任追溯。
   - `date`：标注日期。
   - `evidence_frames`：该判断所依据的帧图的相对路径列表，用于复核。
5. **一致性要求**：单人标注 → 同一人隔日复标同一批（至少 20 条子集），一致率 **≥90%**；「一致」的判定口径二选一并写明（只能选一个）：口径一 `visible_separation_frame` 完全相同；口径二 差异 ≤1 帧（选口径二时须在报告里单列该口径）。多人标注 → 另报 **Cohen's κ**（阈值待用户定）。
6. **产物路径**（均为仓库内相对路径；落库前若目录不存在须新建，并在提交中一并出现）：
   - `golden/visible_separation.jsonl`：标注结果。
   - 抽样脚本及其种子记录（脚本路径落定后回填至本节）。
   - 逐帧帧图目录（每条样本一套，供 `evidence_frames` 与复核使用）。
   - 复标子集结果（至少 20 条）。
7. **标完后如何验收**（下列五项全过，第 1 阶段才算通过，方可进入第 2 阶段；未通过不得调参、不得进第 2 阶段）：
   - [ ] 条数与分布核对：恰好 60 条、不少于 10 个来源、每源不少于 3 条、四档覆盖达标。由脚本断言，不靠人工数。
   - [ ] 字段完整性核对：九个字段齐全、无空值、`fps > 0`、`visible_separation_frame` 为整数且落在该样本帧数范围内。
   - [ ] 逐条自检「可见分离第一帧」定义：第 t 帧可见分离、**第 t-1 帧不可见分离**（首帧即分离时 `t=0` 并在记录中注明），并逐条核对 `evidence_frames` 是否支持该判断。
   - [ ] 复标一致率 ≥90% 达成；未达成的条目逐条给出原因与最终取值。
   - [ ] 抽样人工二次目视复核 10 条（从 60 条中按同一种子随机取），记录一致/不一致条数与不一致原因。

### 3.2 第 2 阶段：自动检测开发与校准

检测在 ROI 区域内做，输出是「第一帧可见分离」的帧号。三条候选规则都要求确定性：同一输入重复运行结果相同，不引入随机种子或采样。校准的对照集就是第 1 阶段的金标准；held-out 20 条从 60 条中划出，不参与规则调参。

帧率必须现场实测。`event_frame` 由 `event_time * fps` 反推，帧率错一位，帧号判据整体失准。判据里的 2 帧误差在 25fps 下约 0.08 s，帧率不是 25fps 时按实测换算。

### 3.3 第 3 阶段：全量重算

重算顺序固定：先出 `event_time`，再按 `pipeline/v3_candidate_plan.py:627` 与 `:659` 的规则裁窗，最后由 `_state_for_interval` 判档。三段分开落盘，任何一段出问题都能定位到具体样本，不必整批重跑。

`event_time_reliable` 的判定要单列。事件时刻重算后，此前因不可靠而判「无法判断」的样本可能转为可用，也可能反向转出。这类迁移逐条记原因，写进差异统计。

### 3.4 第 4 阶段：新数据发布

新 release 带新 `release_id`，旧 release 与旧标签原地保留，作为历史证据与差异对照。契约层面分两种情形：标签集合不变（仍是四档）时 schema 不需改；标签语义一旦改变，必须升 `contract_hash`。契约文件是 `pipeline/contracts/tensile_vlm_v4_1.json`（当前 `contract_hash` 以 `3798f00c...` 开头），哈希常量在 `pipeline/production_contract.py` 的 `EXPECTED_CONTRACT_HASH`。

- **硬要求 A（升哈希）**：若标签语义发生改变，**即使枚举集合不变（四档名字与取值域都没变），也必须升 `contract_hash`**。理由：同一契约编号下不允许并存两套标签定义，否则用同一 `contract_hash` 记录的评测结果无法判断是按哪套标签算的。升哈希必须同时更新 `pipeline/production_contract.py` 的 `EXPECTED_CONTRACT_HASH`，并同步那批冻结断言哈希的测试（不得只改常量留下红测试）。
- **硬要求 B（不升哈希）**：若只是**重算 `event_time` 的数值**（同一锚点定义下把偏移量算准），标签语义定义不变，则**不需要**升 `contract_hash`。
- **两者如何分清**：判据是「**契约正文里标签语义的定义是否改变**」，不是「数据里的数值是否改变」。数值重算不改定义 → B；定义改了口径（含锚点从 `event + 0.5` 的几何偏移改为可见分离第一帧）→ A。**本次重建属 A 一侧**，因为 D1/D2 改变了「已断裂」的语义锚点。

legacy 数据 release 的产物约定沿用现有格式：集合目录配 `index.json`，追加索引后原子写入 `LATEST`。同一集合只允许一个写入进程。整体检查清单见 `docs/plans/2026-10-18-full-chain-validation.md`（14 环节），该文档已入库（commit `aa3fc881`）。

### 3.5 第 5 阶段：用新标签复测

不训练，只推理。用现有 R1 权重、同一 Prompt、同一 425 条划分，只换标签，观察各档 recall 与两轴指标。此前的 recall 数字测的是标签与画面的偏差与本轮改动之外的差异；这一轮是第一次在标签与画面对得上的前提下测量模型能力。

结果解读按三条：各档 recall 是否从零返回非零；两轴指标的分布是否与目视判断一致；分档之间是否出现新的系统性混淆。若「已断裂」仍为 0/33，按第 4 节的结论分支处理。
