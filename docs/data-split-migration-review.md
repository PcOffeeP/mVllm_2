## 旧划分是怎样产生和进入后续链路的

原 [source_bootstrap.py](../../mVllm_2/pipeline/source_bootstrap.py) 的 `stratified_split` 按旧类型和位置分层，默认 seed 42、test ratio 0.2，保留测试集后对其余视频做三折；稀有池进入各折训练。对应 JSON 保存 ID、计数和方法。这里是旧生成器的规则及旧清单的身份，不是依据新标签重新分层；不得因新分布不同而自动重新划分。

旧 [rebuild_data.py](../../mVllm_2/pipeline/scripts/rebuild_data.py) 调用源数据阶段生成快照和划分，但其命令入口已在[脚本索引](../../mVllm_2/pipeline/scripts/SCRIPTS.md)列为停用；这是追溯来源的脚本，不是推荐执行的迁移命令。后续旧版候选规划 [v3_candidate_plan.py](../../mVllm_2/pipeline/v3_candidate_plan.py) 从参考清单读取 development 与 test_audit ID，校验互斥和完整覆盖，并对旧批次硬编码 89/21。具体输入和依赖应在实施授权后再核对；不能把测试审计分支当成测试使用授权。

## 供确认的衔接设计与选择

建议以原视频 ID 和固定划分清单为主索引，给每个派生产物记录来源视频、所属划分、生成配置与人工审核结果；在生成任何片段前检查缺失、重复和跨划分冲突。收益是延续当前划分并能追溯同源片段；代价是必须先确认 ID 与素材身份、异常和缺失项的处置，ID 一致本身不排除近似素材泄漏。具体记录格式与冻结方式仍待确认，不据此修改接口。

需要用户决定或进一步核查：

1. 保留既有划分是当前已确认方向；当核查发现不同 ID 的重复或近似素材、素材身份不符或参考信息泄漏时，如何处置受影响条目，须根据实际问题另行确认。
2. “无法判读”、各字段不确定和异常视频是否进入训练、验证或审查，与第 2 项评价分母同步决定；不能由当前统计自动排除或纳入。
3. 旧脚本使用旧标签与事件时间，当前新标签和不使用时间类标注的边界见 [facts.yaml](facts.yaml) DF-018、DF-019；具体映射和选窗待讨论。下游应记录每个片段来自哪个划分，但源视频标签不能无条件复制到片段。
4. 测试集后续使用时机、候选准入及频率需另行确认；此次覆盖统计不开放测试，也不构成模型评价。

**失效条件：** 新标注表、源视频身份、既有划分或新数据链路的确认规则发生改变时，本审查稿中的对应和统计须重新核对；被新的权威设计取代时作废。
