## 2. 两列帧号

### 2.1 定义

本节效力：两列定义与「`断裂帧_后` 是权威值」属用户裁决（2026-10-19）·已回填（见第 0 节）；「帧号从 0 起计数」属本文档提出的口径说明，待用户确认，确认前不作验收依据。

`断裂帧_前`：该源最后一帧仍连通的帧号，整数。角色是证据。它证明标注者看过相邻两帧，并确认前一帧没有分离。

`断裂帧_后`：该源第一帧已分离的帧号，整数。角色是权威值。真实断裂时刻由这一列决定。

帧号从 0 开始计数。首帧即分离时，权威值为 0（第 5.3 条第 ② 项）。0 起计数与候选级标注口径一致，见 `docs/plans/2026-10-18-label-rebuild.md:164`。

### 2.2 时刻由脚本计算，禁止手填

本节效力：「事件时刻由脚本按实测 fps 计算、禁止手填」与「旧列原样保留」属用户裁决（2026-10-19）·已回填（见第 0 节）。旧列保留另有 DF-013 作仓库记录（`docs/design-facts.yaml:213`–`:218`）。

标注表不出现承载新锚点时刻的列。事件时刻由脚本按 `断裂帧_后 / fps` 计算。fps 取视频实测值，现行代码的取法见 `pipeline/source_bootstrap.py:295`。

理由：手填时刻会带来两类差错：抄错帧号，或按错误的 fps 换算。帧号只有一个整数，便于核对；时刻可以随时重算。

旧列 `断裂时间点` 原样保留，不改写、不换算。它不参与新锚点的计算，只用于新旧锚点的偏差统计与追溯。这条与 `docs/design-facts.yaml:217` 记录的 D1 裁决一致。

旧列 `断裂帧数` 本轮同样原样保留，不参与新锚点。当前代码里它是必需列（`pipeline/source_bootstrap.py:40`），并优先于 `断裂时间点` 参与 `event_frame_effective` 的计算（`:293`–`:297`）。新口径下 `断裂帧_后` 是唯一权威帧号。`断裂帧数` 与 `断裂帧_后` 不一致的源写入第 4.3 节的复核清单逐条核对，不改写旧列。

### 2.3 两列必须相邻（本文档提出，待用户确认）

两列都由标注者填写。相邻约束只对 `已标注·有断裂` 的源生效：取值必须满足 `断裂帧_前 = 断裂帧_后 - 1`。其余三态两列都为空，见第 3.4 节。

理由由定义直接得出：前一帧仍连通，后一帧已分离，中间没有第三帧。

两列不满足该关系时，标注结果自相矛盾。处理办法：以 `断裂帧_后` 为准，把该源写入复核清单，由标注者重看相邻两帧后改正。

例外只有一处：首帧即分离。此时 `断裂帧_前` 留空，`断裂帧_后` 为 0，`标注备注` 写「首帧即分离」。首帧即分离的处置属用户裁决（2026-10-19）·已回填（见第 5.3 节第 ② 项）。本条标为本文档提出的部分仅是相邻约束本身。

本条与第 7 节的 A7 是同一约束：本文档提出，待用户确认；确认前不作验收依据。这一标注只覆盖相邻约束本身，不含首帧即分离的处置。

## 3. 状态列：空值必须按成因区分

### 3.1 四态与行为

本节效力：四态的取值名与行为属用户裁决（2026-10-19）·已回填（见第 1 节与第 0 节）。

| 状态 | 两列帧号 | 行为 |
| --- | --- | --- |
| 已标注·有断裂 | 有值（首帧即分离时 `断裂帧_前` 空） | 正常。该源可产出全部依赖事件时刻的候选 |
| 已标注·无断裂 | 空 | 合法空值。该源照常使用，只产出「未断裂」档候选 |
| 未标注 | 空 | 拒绝（fail-closed）。该源不产出任何候选 |
| 无法判读 | 空 | 拒绝，并单列清单，注明原因类别。严禁并入「无断裂」 |

### 3.2 逐态规定

本节为四态各自的规定，其中四态取值与行为属第 0 节第 1 档（用户裁决·已回填）；本节对「`标注备注` 写什么」的细化由本文档提出，待用户确认。

`已标注·有断裂`：两列帧号都有值，唯一例外是首帧即分离。该源的事件时刻由 `断裂帧_后 / fps` 计算。

`已标注·无断裂`：两列都空，`标注备注` 必须写清判据，例如「只颈缩未断」。这是合法空值，该源照常使用，只产出「未断裂」档候选。不得把它当缺陷，也不得当未完成。现行代码的 `SOURCE_NO_FRACTURE` 分支只产 `stable_negative` 一类窗口，见 `pipeline/v3_candidate_plan.py:669`–`:681`。「`标注备注` 必须写清判据」这一条由本文档提出，待用户确认。

`未标注`：两列都空。该源不产出任何候选，写入跳过清单，原因标为「未标注」。这是迁移期的默认状态，见第 3.3 节。

`无法判读`：两列都空。该源不产出任何候选，同时单列清单。清单按原因类别归入遮挡、离焦或模糊、画面异常、夹具未夹紧、其他五类。不得并入「无断裂」。混同的后果具体：模型会从这段素材学到「此处没有断裂」，而真实情况是「此处看不清」。前者是标签，后者是素材缺陷，两者不能用同一档标签表示。

上述五类原因类别由本文档提出，待用户确认。

状态列的值为空或不在四态之内时，按 `未标注` 处理，并把该源写入复核清单。允许的取值是闭集，不得出现第五种取值。本条归一规则由本文档提出，待用户确认，统计口径见第 7 节的 A6。

### 3.3 迁移规则

本节效力：前三段的迁移规则属用户裁决（2026-10-19）·已回填（见第 0 节）；末段「列缺失与单元格留空分开处理」由本文档提出，待用户确认。

旧标注表没有 `标注状态` 列。旧表的全部源一律视为 `未标注`，直到补标完成。

不得据旧列 `断裂时间点` 静默推断状态。旧列的时间与可见分离不保证对齐，据它推断会把旧口径的偏差带进新状态列。

迁移期不得打开旁路，例如「`断裂时间点` 有值即算已标注」。这类旁路会让未补标的源按旧口径继续产出候选，违反第 7 节 A4 的「不回落旧列」要求（A4 实施后才可执行，前提见第 7 节）。

列缺失与单元格留空分开处理。旧表整列缺失时只记一条迁移状态，全表视为 `未标注`，不逐行产生复核清单；逐行清单只针对已有该列但单元格为空的源。这条区分由本文档提出，待用户确认。

## 4. 与既有列的一致性校验

### 4.1 与 `has_fracture` 交叉比对

只对已标注的源比对。`未标注` 与 `无法判读` 的源不参与比对，因为它们不产出候选。

| `标注状态` | `has_fracture` | 结论 |
| --- | --- | --- |
| 已标注·有断裂 | true | 一致 |
| 已标注·有断裂 | false | 不一致，单列清单 |
| 已标注·无断裂 | false | 一致 |
| 已标注·无断裂 | true | 不一致，单列清单 |

表格只列归一后落在 `{true,1,yes,是}` 或 `{false,0,no,否}` 的原始单元。比对取**原始 CSV 单元**，不取记录层的归一值；取值来源是 `all_videos_tag.csv` 的 `has_fracture` 列原文。取原始单元这一口径由本文档提出，待用户确认。

原始单元按 `strip().lower()` 归一后再判定：落在 `{true,1,yes,是}` 或 `{false,0,no,否}` 的视为可比对；空单元、`nan` 与其他文本记「无法比对」，写入第 4.3 节的清单。大小写与首尾空白不参与判定，`FALSE`、`False`、`false` 是同一个值。仓库测试的固定装置写的正是大写（`tests/test_source_bootstrap.py:53`–`:54`、`tests/versioning/test_data_pipeline.py:1147`）。

记录层对同一个原始单元的处理不同，两个口径不可混用。`pipeline/source_bootstrap.py:231` 把原始单元交给 `_parse_bool_or_none`（`:178`–`:184`），再把结果写入记录的 `has_fracture`（`:313`）。该函数把空单元归一为 `False`（`:182`–`:183`；`_read_csv` 已在 `:168`–`:171` 把缺字段转成 `""`，空单元格本就是 `""`），把 `nan` 归一为 `None`（`:184`）。所以记录的 `has_fracture` 只有 `True`、`False`、`None` 三种取值，没有空字符串，只看记录分不出「CSV 写了 false」与「CSV 留空」。这就是本节比对取原始单元的原因。

两种口径的差异集中在一处：原始单元为空的源，在记录层得到一个 `False`，在本节的比对侧记「无法比对」。两处不矛盾，用途不同：记录层要给下游一个可用布尔值，比对侧要找出「表里根本没写」的源。所以「空单元归一为 `False`」只在记录层成立，不适用于本节比对。

### 4.2 与 `is_abnormal` 交叉比对

`标注状态` 为 `已标注·有断裂` 或 `已标注·无断裂`，而 `is_abnormal` 为 true 时，记为不一致并单列清单。`is_abnormal` 的原始单元同第 4.1 节的归一集合：按 `strip().lower()` 归一后落在 `{true,1,yes,是}` 的按 true 比对，落在 `{false,0,no,否}` 的按 false 比对；空单元、`nan` 与其他文本记「无法比对」，进第 4.3 节的清单。交叉比对本身属用户裁决（2026-10-19）·已回填的范围（一致性校验），比对的具体范围由本文档细化，待用户确认。理由：夹具未夹紧与视频异常这两类源，按第 3.2 节的原因类别应落在 `无法判读` 一侧，不该落在已标注一侧。

### 4.3 不一致怎么处理

本节的三类清单条目与共用字段由本文档提出，待用户确认。其中「交叉不一致」的比对要求属第 0 节第 1 档（用户裁决·已回填）。

不一致时报警并单列清单，不得静默取任一边。清单有三类条目，三类共用一套字段：源标识、`标注状态` 值、`has_fracture` 值、`is_abnormal` 值、`断裂帧数` 值、`断裂帧_后` 值，以及判读依据。

1. 交叉不一致：`标注状态` 与 `has_fracture` 或 `is_abnormal` 对不上（第 4.1 节、第 4.2 节）。
2. 无法比对：原始单元是空单元、`nan` 或其他文本，判不出该源是否一致（第 4.1 节、第 4.2 节）。
3. `断裂帧数` 差异：旧列 `断裂帧数` 与 `断裂帧_后` 不一致（第 2.2 节）。

「无法比对」不计入 A5 的「不一致」数，该口径的归属随第 7 节 A5 的标注。它标记的是表内单元没写清。本节只规定这类条目仍须逐条列出并给出结论。

不一致数不要求为 0。要求是每一条都能解释：要么标注错了，要么旧列错了，要么该源本属 `无法判读`。逐条给出结论后改正相应单元。

### 4.4 `has_fracture` 自身要复核

`has_fracture` 在本次重标中同样要复核，它不是可信的对照物。它的结论不作状态列的依据。本条由本文档提出，待用户确认。

现行代码里两者的从属方向与此相反：canonical 值由 `断裂模式` 决定。`has_fracture` 在本链路上只作冲突检测与缺键兜底，不作权威：缺 `has_fracture_canonical` 键时以 `has_fracture` 顶替（`pipeline/v3_candidate_plan.py:140`、`pipeline/review_evidence.py:118`）。`pipeline/review_evidence.py:144`–`:151` 是另一种缺值处理：`has_fracture_canonical` 键存在但值为 `None` 时同样回落，显式取 `has_fracture`，再按 `True`、`False`、其余三种结果分派 `SOURCE_FRACTURE`、`SOURCE_NO_FRACTURE`、`SOURCE_VIDEO_ABNORMAL`。`:118` 的回落靠 `dict.get` 的默认参数，只在缺键时生效。两处语义不同，本节结论不变。冲突时记入 `label_governance_reason` 并置 `is_label_conflict`，记冲突的位置按分支列出：`FRACTURE_TYPES` 分支在 `has_fracture=False` 时记一条（`pipeline/source_bootstrap.py:244`–`:246`）；`未断裂` 分支在 `has_fracture=True` 与 `is_abnormal=True` 时各记一条（`:253`–`:255`、`:256`–`:258`）；`未夹紧` 分支在 `has_fracture=True` 时记一条（`:267`–`:269`）；`else` 分支（`断裂模式` 未知）无条件记一条「未知 type」冲突（`pipeline/source_bootstrap.py:280`、`:286`）；`canonical_abnormal` 为真的源，在 `location` 不属于 `N/A` 或空串时再记一条「异常视频 location_canonical 强制为 null」（`:289`–`:291`）。`:274`–`:279` 另有一处 `has_fracture` 参与 canonical 判定（`视频异常` 分支据它取 `True` 或 `None`），但不记冲突原因。新口径把权威方向改为状态列为准、`has_fracture` 为对照项。

## 5. 「什么算可见分离」

本节口径属用户裁决（2026-10-19）·已回填（可见分离的定义与四条边界情形）；第 5.4 节的判读步骤由本文档按该口径排成执行顺序，不新增判据。

### 5.1 算

判据落在两点，两点都满足才算可见分离：

1. ROI 内试样断开成**至少两个**互不连通的区域。
2. 断开处出现能看见背景的贯穿缝隙。

正例的形态：缝隙贯穿试样整个宽度，缝隙内露出背景的颜色与纹理。两段材料的位置在后续帧继续分开。

### 5.2 不算

下列情形容易被误判为可见分离，逐条给判读说明。

颈缩变细但仍连通：试样局部变窄，两侧材料仍连着。变窄处没有贯穿缝隙，只有轮廓收窄。

出现裂纹但两段仍相连：能看到深浅不一的纹路，纹路两侧材料仍连成一片。裂纹未贯穿整个宽度。

离焦或运动模糊造成的局部变暗：该处像素变暗，暗区边界糊，形状随帧漂移。反例：缝隙两侧颜色仍连续，只是比周围暗，那是阴影，不是缝隙。

试样与背景颜色接近造成的假性断开：看似断开的位置，两侧像素沿边缘仍连续过渡。判读时看边界是否突然中断，不要只看明暗差。

夹具或手部遮挡造成的视觉中断：中断区域的边界超出试样轮廓，遮住的是背景。遮挡物本身有形状，会随帧移动。

### 5.3 四条边界情形

① 渐变断裂（韧性）：取「贯穿缝隙首次覆盖试样整个宽度」那一帧。缝隙从局部扩展到全宽的过程中，只覆盖一部分的帧不算分离。

② 首帧即分离：`断裂帧_前` 留空，`标注备注` 写「首帧即分离」，`断裂帧_后` 取 0。

③ 全程无可见分离（只颈缩未断）：填 `已标注·无断裂`。不得留成 `未标注`，也不得填 `无法判读`。

④ 多处开裂：取第一处出现贯穿缝隙的位置与帧。后续开裂点不改 `断裂帧_后`，可写进 `标注备注`。

### 5.4 判读步骤

1. 打开该源的视频与 ROI 决定，确认判读范围限定在 ROI 内。ROI 之外的画面不作判据。
2. 先看末帧，判断末帧是分离态还是连通态。
3. 末帧为分离态时，从末帧逐帧向前看，找第一个连通帧。该连通帧的帧号是 `断裂帧_前`，它的后一帧是 `断裂帧_后`。末帧为连通态时，直接跳到第 6 步。
4. 复核第 3 步的两帧：前一帧必须连通，后一帧必须分离。若前一帧也分离，继续向前找。
5. 填 `断裂帧_前`、`断裂帧_后`，`标注状态` 填 `已标注·有断裂`。
6. 全片都找不到分离态，且有明确判据（只颈缩、纹路未贯穿），填 `已标注·无断裂`，并在 `标注备注` 写判据。
7. 画面无法支撑判断（原因类别取第 3.2 节的五类），填 `无法判读`，在 `标注备注` 写具体原因，并把该源写入「无法判读」清单。

列定义与读取白名单的具体落点：`_read_csv` 只校验必需列是否存在，缺少即抛错（`pipeline/source_bootstrap.py:530` 传入 `TAG_COLUMNS`，缺列即抛错见 `:165`–`:167`），多出的列不报错。

多出的列不进入 records，原因在 `_governed_record`，与 `TAG_COLUMNS` 无关。`_read_csv` 返回整行全部列的 dict（`:168`–`:171` 用 `row.items()` 取值，不按 `TAG_COLUMNS` 过滤）。records 由这张整行表构造：`tag_index` 直接取自 `_read_csv` 的结果（`:552`），再交给 `_governed_record`（`:640`–`:643`）。`_governed_record`（定义在 `:225`，返回记录在 `:300`–`:322`）按固定键集逐项取值，多出的列在它这里被丢掉。新列要进入 records，只需在 `_governed_record` 增加读取；是否会被必需列门拒绝，取决于是否把它加进 `TAG_COLUMNS`。`_normalized_rows` 的产物只喂 `normalized_rows_sha256`（`:711` → `:720`–`:722`），与 records 无关。

`TAG_COLUMNS` 定义在 `pipeline/source_bootstrap.py:32`，生产代码有四处直接引用（`pipeline/source_bootstrap.py:530`、`:711`、`:719`，`versioning/data_pipeline.py:1005`）与一处派生产物（`:720`–`:722` 用 `normalized_tags`，不直接引用 `TAG_COLUMNS`），性质分三类，改动时会互相牵扯。

两处是必需列门，缺列即抛错：

1. `pipeline/source_bootstrap.py:530` 以 `TAG_COLUMNS` 调 `_read_csv`，缺列抛错见 `:165`–`:167`。
2. `versioning/data_pipeline.py:1005` 以 `source_api.TAG_COLUMNS` 调 `_read_source_rows`（`tags = _read_source_rows(inputs.tags, source_api.TAG_COLUMNS)`）。该 reader（`versioning/data_pipeline.py:845`–`:860`）同样把 `columns` 当必需列，缺列或重复列即抛错（`:853`–`:854`）。

这两处都不拒绝多余列。第三处是读取白名单：`_normalized_rows` 在 `:711` 接收 `columns=TAG_COLUMNS`，在 `:515` 用 `row.get(column, "").strip()` 逐列取值。这一处不拒缺列，缺列一律填空串。`TAG_COLUMNS` 在这一处的过滤只作用于 `normalized_rows_sha256`（`:711` → `:720`–`:722`），记录本体不走这条路径。这一处不拒缺列的行为与它的用途一致，也说明它不能兼任必需列门。

后两处把 `TAG_COLUMNS` 写进身份材料：`:719` 把 `list(TAG_COLUMNS)` 写入 `csv_contracts["all_videos_tag.csv"]["columns"]`；`:720`–`:722` 用 `_normalized_rows` 的结果算 `normalized_rows_sha256`。这两项随 `csv_contracts` 进入 `annotation_inventory`（`:731`），随 `annotation_inventory` 进入 `source_identity`（`:749`），最终决定 `snapshot_id`（`:758`–`:759`）。`annotation_inventory` 每项除展开的 `**csv_contracts[name]`（`:734`）外，还含 CSV 文件的 `sha256`（`:733`）。

把新列直接加进 `TAG_COLUMNS`，旧表会在两处必需列门被拒（`pipeline/source_bootstrap.py:530`、`versioning/data_pipeline.py:1005`），与第 3.3 节的迁移路径冲突：「旧表整表视为 `未标注`」要求旧表仍能读入。白名单（`:711` 传入、`:515` 逐列取值）不拒缺列，缺列一律填空串。这正是需要把「必需列集合」与「可选白名单」拆开的理由：必需列门要求每一行都有该列，白名单允许旧表缺列，两处行为不同。

增列还会改变身份，两条路径各管一类情况。

一条来自 `TAG_COLUMNS` 本身：`csv_contracts.columns` 与 `normalized_rows_sha256` 都取自 `TAG_COLUMNS`（`:719`、`:720`–`:722`）。表文件一个字节没动、只改 `TAG_COLUMNS` 的内容，也会算出不同的 `source_identity` 与 `snapshot_id`。

另一条来自文件级哈希：`annotation_inventory` 还含 CSV 文件级 `sha256`（`:733`）。同一份表新增一列，文件字节就变了，`source_identity` 与 `snapshot_id` 随之改变，与是否改 `TAG_COLUMNS` 无关。

所以「同一份未变的表会算出不同身份」只适用于前一条：表不变而代码里的列清单变了。表本身新增列属于后一条。实施时须明确 `csv_contracts.columns` 与 `normalized_rows_sha256` 取「必需列集合」还是「取并集」，否则同表不同身份。

测试装置随 `TAG_COLUMNS` 自动跟随：`tests/versioning/test_data_pipeline.py:1143` 用 `dict.fromkeys(TAG_COLUMNS, '')` 构造标签行，`:1152` 用 `TAG_COLUMNS` 写表头；`tests/test_source_bootstrap.py:41`、`tests/test_rebuild_source_only.py:51`、`tests/test_artifact_index.py:43` 用 `{column: "" for column in TAG_COLUMNS}` 构造标签行，表头由 `TAG_COLUMNS` 写出（`tests/test_source_bootstrap.py:72`–`:74`、`:220`，`tests/test_rebuild_source_only.py:82`，`tests/test_artifact_index.py:74`–`:76`）。这些装置会随 `TAG_COLUMNS` 补齐新列的空值。

仓库另有硬编码 tag 表头的测试装置：`tests/test_audit_review_decisions.py:24`、`:50` 用 `fieldnames` 字面量写死 9 列，不随 `TAG_COLUMNS` 变化。其被测对象 `pipeline/scripts/archive/audit_review_decisions.py` 不引用 `TAG_COLUMNS`（`grep` 无命中），读标注表走 `csv.DictReader`（`:192`），缺少的列不抛错。两处装置不会随 `TAG_COLUMNS` 补齐新列，本轮不受影响；实施时如要这两处也用上新列，需单独改它们。

实施任务必须把「必需列集合」与「可选白名单」拆开，或把新列设为可选，并写死 `versioning/data_pipeline.py:1005` 这次调用传必需列部分还是并集。如果不写死，新列要么在新链路读不到，要么旧表在新链路被拒。还要把列缺失与单元格留空区分开：整列缺失只记一条迁移状态，单元格留空按第 3.2 节归一。这几点是实施改动点，本轮不改。

旧列的处置同时写进这份清单：`断裂时间点` 与 `断裂帧数` 都原样保留、都不作新锚点的依据。`断裂帧数` 仍是必需列（`pipeline/source_bootstrap.py:40`），继续留在 `TAG_COLUMNS`；`断裂帧_后` 是唯一权威帧号。
