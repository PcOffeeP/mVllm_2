# ADR-0001：采用可读版本控制与单向记录链路

- 状态：已接受
- 日期：2026-09-01
- 适用范围：可读版本控制新体系 `versioning/`

## 背景

旧链路以哈希身份、集合索引和 `LATEST` 指针组织部分数据与模型产物，适合内容寻址，
但不适合作为人日常操作和跨工具追踪的统一身份。新体系需要让数据、Prompt、训练、模型、
测评各自拥有明确、可读、不可猜测的正式身份，同时保留数据处理、实际运行记录和 Git
同步之间的清晰边界。

## 决策

1. 正式身份分为 data、prompt、train、model、eval 五类，统一使用
   `<kind>-v<协议>-r<N>` 完整名称。写入和晋级操作必须显式给出完整身份；不提供哈希身份、
   `LATEST`、短前缀或隐式当前版本选择。
2. Git/YAML 管运行定义、Prompt、代码、文档和从 MLflow 导出的轻量 manifest；DVC 只管理
   数据 pipeline 与数据产物；MLflow 管实际训练、模型、指标、测评和运行状态。
3. 记录流向固定为 Git/YAML + DVC 定义输入 → 实际运行 → MLflow 完整记录 → 单向导出
   manifest → Git 同步。manifest 是机器生成的人类可读快照，不反向写回 MLflow，也不与
   MLflow 分字段共同担任权威。
4. 数据、Prompt、训练、模型和测评按各自生命周期封存；可由程序判断的边界一律
   fail-closed。holdout 保留训练禁用、真值隔离、稳定路径预注册冻结、按内容摘要绑定的
   全局一次性 claim，以及完成时的不可覆盖消费证据；跨机器恢复不绑定本地绝对路径。
5. 模型使用两阶段 Registry 生命周期：完成训练先登记 staging Model Version，正式 eval
   必须精确引用其可读身份和 MLflow 数值版本；eval 通过后再单向绑定 `eval_id`，此后才允许
   candidate/production 晋级。
6. `pipeline/`、`finetune/` 的 legacy 身份和索引规则继续只读保留，正式迁移完成前不删除、
   不批量改名，也不把其规则带入 `versioning/`。

完整字段、状态机、备份与恢复细节由
[可读版本控制架构设计](../plans/2026-09-01-readable-version-control-design.md)维护。

## 结果

- 日常命令和跨工具引用具有稳定、可读的完整身份，冲突时直接停止而不是猜测。
- 同一类事实只有一个权威系统，减少 Git/YAML 与 MLflow 双向同步和漂移风险。
- legacy 与新体系在迁移期并存，需要继续维护明确分域；核心基础设施完成不代表真实产物
  已迁移，也不代表模型质量已经验收。
- DVC/MLflow 的内部哈希或数值主键仍可作为工具内部实现，但不成为人的正式版本名。
