## 1. 从输入到审查

```text
冻结输入 + ROI 阶段产物 + 批次
             ↓
按开发集和测试审计的源视频清单规划候选
             ↓
按时间窗口生成候选区间及默认标签
             ↓
裁剪视频 → 按预处理器采样 → 检查采样门禁
             ↓
通过的候选进入清单；未通过的候选记录排除原因
             ↓
审查导出 → 人工审查 → 审查结果回收 → 开发集发布
```

入口为 `python -m versioning data subvideo`，需要显式指定根目录、冻结输入和批次。它读取 ROI 阶段清单、预处理器配置及文件，以及开发集和测试审计的参考记录；两组源视频分别规划，测试候选的 scope 为 `test_audit`。参考记录还参与部分窗口选择与匹配。

### `development` 和 `test_audit` 对应哪些既有划分

| 候选 scope | 源视频范围 | 与训练、验证、测试的关系 |
| --- | --- | --- |
| `development` | 显式输入清单中的全部视频 ID，减去既有 `test` ID。 | 包含既有训练和验证源视频；不是另划一份“开发集”，也不等同于某一折的验证集。 |
| `test_audit` | 显式 `test` 清单中的源视频 ID。 | 作为测试审计范围独立规划，不进入本文所述开发集发布分支；有这个分支不等于本轮获准使用 test。 |

`_load_media_inputs` 要求两份历史参考的 `source_inventory` 分别精确对应上述集合，再由 `run_input_subvideo` 分 scope 调用规划器。已完成的[划分 ID 对照](data-split-migration-review.md)记录开发集 89 个、测试集 21 个；各折 train 与 val 的并集均为同一批 89 个开发 ID。该数量是既有清单的核查结果，不是本入口重新划分或本轮视频已生成的证据。

后续开发集发布还检查入选片段的源视频是否被每折 train/val 覆盖，且不与 test 交叉。片段沿源视频划分归属，不因生成窗口变成新的划分单位。

代码位置：[阶段分派和子视频阶段](../../mVllm_2/versioning/data_pipeline.py) 的 `run_stage`、`_load_media_inputs`、`run_input_subvideo`、`_input_release_rows`。

## 3. 片段窗口怎样选

### 通用规则

| 项目 | 代码规则 |
| --- | --- |
| 目标时长 | 尝试 2、3、5、10、20 秒；不是每个源视频都能产生所有时长 |
| 帧对齐 | 按 ROI 视频的帧率和总帧数确定起止帧，并记录对应时间和时长 |
| 最短时长 | 候选不足 1 秒时不加入 |
| 事件保护间隔 | 事件前、后各留 0.5 秒；断前或断后窗口不跨入该间隔 |
| 去重和上限 | 帧区间与状态相同的候选去重；每个源视频的各角色上限见下表 |
| 状态检查 | 窗口推导出的状态必须符合该窗口角色的预期，否则不加入 |

**两种时长检查不能混用：**

| 判据 | 含义与状态 |
| --- | --- |
| 旧代码最短候选 1 秒 | 控制单个候选是否够长，已存在于代码。 |
| DF-015 的事件后至少 2 秒 | 检查事件时刻之后、guard 之外是否还留有足够素材，不足则不生成 post 候选；尚未落实到旧代码。 |

后续方案需明确 DF-015 的接入对象与检查位置，未经确认不取消或调整该要求。

代码位置：[候选规划](../../mVllm_2/pipeline/v3_candidate_plan.py) 的常量、`_aligned_interval`、`_raw_candidates_for_source`。

### 按源视频类型选窗口

| 源视频 | 窗口 | 选择方式 |
| --- | --- | --- |
| 断裂 | 包含事件 | 尝试不同目标时长和事件相对位置；标准窗口放不下时，还会尝试自适应窗口 |
| 断裂 | 事件前 | 根据源断裂类型选择靠近事件的窗口，或在事件前区间取前、中、后窗口 |
| 断裂 | 事件后 | 从事件时间加 0.5 秒开始，可取完整剩余段及其分段 |
| 未断裂 | 未断裂窗口 | 在整段视频中按目标时长取窗口；位置由视频 ID 的哈希确定性轮换 |

### 事件位置与各角色数量上限

`EVENT_POSITIONS = (0.20, 0.35, 0.50, 0.65, 0.80)`，即 **20%、35%、50%、65%、80%**。它在两个分支中的含义不同：

- **包含事件窗口：** 比例表示事件位于片段内部的相对位置。例如目标时长为 5 秒、比例为 20% 时，先尝试从事件前 1 秒到事件后 4 秒的窗口，再按帧对齐。代码对五个目标时长轮换配对这些比例，依据历史参考匹配分数选两组模板，最多形成 10 个标准模板；不是枚举全部 25 种组合。标准窗口放不下时，另收集自适应窗口，最终最多补入其中 1 个，仍受 transition 总上限约束。
- **未断裂窗口：** 同组比例表示候选中心在整段源视频中的目标位置；由视频 ID 哈希确定性轮换，与各目标时长配对。靠近边界时窗口会平移到视频内，不表示存在断裂事件。

以下数量均是**每个源视频、每个角色的规划上限**，不是保证产出数。断前类型按旧 `type` 映射后的机制判断，不是直接读取本轮五类标注。

| 窗口角色 | 适用条件与取法 | 上限及常量 |
| --- | --- | --- |
| 包含事件 `transition` | 断裂源且事件时间可靠；按上述标准模板与自适应补充选窗。 | 10，`TRANSITION_CAP`。 |
| 事件前 `pre_event`：韧性类 | 旧机制为韧性断裂或半脆半韧断裂；对能放入断前区间的目标时长，取前、中、后位置（`PROCESS_POSITIONS = 0/0.5/1`）。 | 15，`DUCTILE_PRE_EVENT_CAP`。 |
| 事件前 `pre_event`：脆性类 | 旧机制为脆性断裂或爆炸性断裂；窗口末端贴近事件前 guard 边界。可用目标时长超过 3 个时，选最短、中间和最长。 | 3，`BRITTLE_PRE_EVENT_CAP`。 |
| 事件前 `pre_event`：其他 | 其余旧机制；窗口末端贴近事件前 guard 边界。五个目标时长均可用时取 2、5、10、20 秒，否则取可用列表的前 4 个。 | 4，`OTHER_PRE_EVENT_CAP`。 |
| 事件后 `post_event` | 从事件加 guard 后取完整剩余段；剩余段至少 6 秒时另分 3 段，至少 3 秒但不足 6 秒时另分 2 段，不足 3 秒时仅保留完整段。 | 4，`POST_EVENT_CAP`。 |
| 未断裂 `stable_negative` | 明确未断裂的源视频；按目标时长及哈希轮换的中心位置选窗。 | 5，`NORMAL_NEGATIVE_CAP`。 |

实际规划数还会因源视频或事件前后长度不足、帧对齐、同帧区间与状态去重、状态不符等减少；后续采样门禁和人工审查还可能排除候选。post 的完整段和分段也都要满足旧最短 1 秒要求，任一分段不满足时会退回仅完整段；这仍不等于落实 DF-015。

包含事件的窗口会参考历史记录：已批准或已修正的记录中，帧范围和标签均完全一致的数量会影响模板排序。

代码位置：[候选规划](../../mVllm_2/pipeline/v3_candidate_plan.py) 的常量、`_transition_templates_for_source`、`_selected_pre_event_durations`、`_normal_negative_window`、`_post_event_windows`、`_raw_candidates_for_source`。

## 4. 默认标签怎样确定

### 第一步：按窗口确定断裂状态

下表中的“事件”指源记录提供的可靠事件时间。条件按代码顺序判断。

| 条件 | `clip_state` |
| --- | --- |
| 源视频为未断裂 | 未断裂 |
| 断裂源的片段结束时间 ≤ 事件时间 − 0.5 秒 | 未断裂 |
| 断裂源的片段开始时间 ≥ 事件时间 + 0.5 秒 | 已断裂 |
| 断裂事件严格位于片段开始和结束之间 | 发生断裂 |
| 其他情况 | 无法判断 |

规划器最终只保留与窗口角色预期状态相符的候选。例如，事件前窗口必须得到“未断裂”。

### 第二步：填充其他字段

| 字段 | “发生断裂”或“已断裂” | 其他状态 |
| --- | --- | --- |
| `fracture_mechanism`、`root_break` | 按源记录 `type` 的旧类型映射填写；未匹配时为 `null` | `null` |
| `location` | 仅保留合法的 `location_canonical`：`inside_gauge` 或 `outside_gauge` | `null` |
| `special_case` | `null` | 仅“无法判断”时取源类别对应的特殊情况 |

未夹紧和视频异常源在候选规划时会被跳过；“无法判断”也不符合正常窗口角色的预期状态，因此不能把 `special_case` 的字段规则理解为这些源会正常生成候选。

例如，旧类型“韧性断裂”映射为韧性机制和 `root_break=false`；“齐根断裂”映射为机制 `null` 和 `root_break=true`。代码会校验字段和组合。**时间与源标签推导出的结果，即使内部自洽，也不能证明画面中的标签正确。**

代码位置：[候选规划](../../mVllm_2/pipeline/v3_candidate_plan.py) 的 `_state_for_interval`、`_candidate_labels`；[v3 标签规则](../../mVllm_2/pipeline/v3_labels.py) 的 `_LEGACY_TYPE_MAP`、`map_legacy_fracture_type`、`validate_v3_labels`。

## 5. 裁剪和采样怎样把关

代码按候选起止帧裁剪 ROI 视频，生成子视频，并依据冻结的预处理器生成采样帧和映射。视频与采样映射经过检查后，才会进入成功物化的候选清单。

| 检查对象 | 规则或结果 |
| --- | --- |
| 发生断裂候选 | 采样须覆盖事件前，以及事件时或事件后 |
| 断前、断后候选 | 采样不得越过各自的 0.5 秒保护边界 |
| 采样门禁不通过 | 排除候选并记录原因 |
| 预处理器指纹不一致、采样数超限等 | 阶段失败 |
| 阶段清单 | 记录规划、成功物化、排除和跳过的信息 |

代码位置：[子视频阶段](../../mVllm_2/versioning/data_pipeline.py) 的 `run_input_subvideo`；[媒体处理](../../mVllm_2/pipeline/v3_candidate_media.py) 的 `build_crop_command`、`validate_actual_sampling_gate`。

## 6. 默认标签如何进入审查

### 规划标记与审查队列

| 阶段 | 对象 | 处理 |
| --- | --- | --- |
| 候选规划 | “发生断裂”“已断裂” | 标记 `manual_required` |
| 候选规划 | 普通“未断裂” | 标记 `automatic_validation` |
| 开发集审查导出 | 已物化的断裂候选 | 加入审查包，生成 v4.1 建议标签 |
| 开发集审查导出 | 源类型恰为“韧性断裂”，且窗口为 `pre_event_back` 的特定断前候选 | 也加入审查包，生成“临界未断裂”建议标签 |
| 测试审计导出 | `test_audit` 候选 | 使用独立的 scope 分支 |

规划标记不是审查完成证明。尤其是特定断前候选：规划时可标为 `automatic_validation`，审查导出仍会把它选入人工审查。

### 回收与发布

1. `review_import` 要求回收结果与导出批次和清单绑定，完整覆盖审查队列，并通过标签及证据检查。
2. 开发集发布时，需要人工审查的候选若缺少决定，会报错；被标为丢弃或需要重新生成的候选被排除。
3. 未进入人工队列的候选，只有转换并校验为普通“未断裂”标签时才能自动准入。

代码位置：[候选规划](../../mVllm_2/pipeline/v3_candidate_plan.py) 的 `_build_scope_candidates`；[审查及发布阶段](../../mVllm_2/versioning/data_pipeline.py) 的 `run_input_review_export`、`_validate_input_review_return`、`_input_release_rows`；[审查候选规则](../../mVllm_2/pipeline/v4_1_review_workflow.py) 的 `_is_incipient_candidate`、`_proposal`。
