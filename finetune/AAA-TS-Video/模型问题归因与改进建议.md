# MiniCPM 视频任务问题归因与下一轮改进建议

## 1. 结论摘要

当前三折模型已经具备一定的 **JSON 格式跟随能力**，但尚未形成稳定的 **时间定位能力** 和 **闭集模式判断能力**，因此联合任务目前不可用。  
更具体地说，模型现在更像是“会按要求输出 JSON”，而不是“能基于视频完成断裂时间与模式识别”。

## 2. 关键结果概览

| 任务 | 关键指标 | 当前表现 | 结论 |
| --- | --- | --- | --- |
| 时间定位 | 可解析时间 / Hit@2s / MAE | `38/83`、`6.02%`、`242.67s` | 基本不可用 |
| 模式判断 | Accuracy / Macro-F1 | `9.18%`、`0.01698` | 严重塌缩 |
| 联合任务 | JSON 合规 / 联合成功 | `81/83`、`0/83` | 会输出 JSON，但不能完成任务 |

上述数字直接来自：

- `AAA-TS-Video/validation/results/time_eval/time_metrics.json`
- `AAA-TS-Video/validation/results/type_eval/type_metrics.json`
- `AAA-TS-Video/validation/results/joint_eval/joint_metrics.json`

补充观察：

- 类型混淆矩阵见 `AAA-TS-Video/validation/results/type_eval/type_confusion_matrix.png`
- 类型分类几乎全部落到 `脆性断裂`
- 时间输出集中在 `7/6/5/null`
- 还出现了日期型字符串被当成时间的现象，例如 `2023-10-20 16:47:50.000`

## 3. 问题归因

### 3.1 时间任务发生了明显的“短时值/空值塌缩”

现象：

- 83 个可评测样本里，只有 38 个给出了可解析时间。
- 可解析时间的中位数是 `7.0s`。
- 高频输出几乎被几个固定值占据：`7` 出现 21 次，`6` 出现 4 次，`5` 出现 2 次。
- 还出现了明显错误的日期字符串，例如：
  - `{"time": "2023-10-20 16:47:50.000"}`
  - `{"time": "2024-05-21 10:24"}`

代表性样本：

```json
{"time": null}
```

对应样本 `video_0053`，GT 时间为 `148.16s`，被记为 `time_unparseable`。

```json
{"time": "7"}
```

对应样本 `video_0006`，GT 时间为 `21.50s`，被记为 `time_threshold_exceeded`。

```json
{"time": "2023-10-20 16:47:50.000"}
```

对应样本 `video_0097`，GT 时间为 `33.22s`，解析后变成 `2023.0`，产生极大误差。

判断：

- 模型没有真正学会在视频时序上定位断裂点。
- 当前输出更像是在“生成一个看起来像时间的字符串”，而不是从视频中回归断裂时刻。

### 3.2 类型任务发生了单类别塌缩

现象：

- 整体 `Accuracy = 9.18%`，`Macro-F1 = 0.01698`。
- 类型预测分布为：
  - `脆性断裂`：97 次
  - `韧性断裂`：1 次
- 混淆矩阵显示，除 GT 本身就是 `脆性断裂` 的样本外，几乎所有类别都被压到了 `脆性断裂` 一列。

代表性样本：

```json
{"type": "脆性断裂"}
```

这条回答同时出现在 `界面脱粘`、`视频异常`、`齐根断裂`、`界面脱粘、齐根断裂` 等多个 GT 类别上。

判断：

- 这不是边界样本难分，而是输出分布已经塌到单个类别。
- 模型目前没有形成稳定的闭集标签判别能力。

### 3.3 联合任务学到了“格式”，但没有学到“任务”

现象：

- 联合任务中 `json_valid_count = 81/83`，说明格式跟随能力其实不差。
- 但 `time_within_threshold_count = 3/83`，`type_correct_count = 19/83`，`joint_success_count = 0/83`。
- 主失败原因排序非常集中：
  - `time_threshold_exceeded = 59`
  - `time_unparseable = 19`
  - `type_mismatch = 3`
  - `json_invalid = 2`

代表性样本：

```json
{"time": "5.28s", "type": "韧性断裂"}
```

对应样本 `video_0053`，GT 为 `界面脱粘`、`148.16s`，说明模型能产出合规结构，但内容不对。

```json
[
  {"time": null, "type": "断裂"},
  {"time": null, "type": "断裂"},
  {"time": null, "type": "断裂"}
]
```

对应样本 `video_0075`，属于 `json_invalid`。

判断：

- 联合任务不是“完全不会答”，而是“只学到回答形式，没学到视频语义”。
- 现阶段继续单看 JSON 合规率没有意义，核心瓶颈已转到任务语义本身。

### 3.4 训练与推理配置之间存在明显错位

直接可见的配置事实：

- 训练配置里 `video_maxlen: 36`
- 当前推理脚本固定 `8` 帧采样
- 训练数据是 `time / type / joint` 三种问法混合
- 当前单任务评测 prompt 更硬，且对输出结构约束更强
- 训练配置注释多次强调“增强 JSON 格式约束能力”“确保模型深刻记忆 JSON 格式”
- 当前 GT 类型分布明显不均衡，`韧性断裂` 占 `48/98`

判断：

- **帧数错位** 很可能直接伤害时间定位能力，尤其是长视频样本。
- **混合任务训练 + 硬单任务推理** 可能放大了输出塌缩，导致模型在 `time-only` 和 `type-only` 下退化成模板回答。
- **类别分布不均衡** 会进一步推动类型预测向少数“默认答案”塌缩。
- **8 epoch 且缺少显式验证约束**，可能让模型更偏向记住格式，而不是在验证集上学到可泛化的任务边界。

## 4. 根因到证据映射

| 根因 | 直接证据 | 现象 | 推断强度 |
| --- | --- | --- | --- |
| 时间任务塌缩 | `time_metrics.json`、原始 `time/*.jsonl` | 高频输出 `7/6/5/null`，Hit@2s 极低 | 强 |
| 类型任务单类塌缩 | `type_metrics.json`、`type_confusion_matrix.csv` | 97/98 次输出 `脆性断裂` | 强 |
| 联合任务只学到格式 | `joint_metrics.json`、`joint_failures.csv`、原始 `joint/*.jsonl` | JSON 合规高，但联合成功为 0 | 强 |
| 帧数与任务设置错位 | 训练 YAML、推理配置、数据分布 | 训练 36 帧、推理 8 帧；混合问法训练，单任务硬提示评测 | 中等 |
| 训练目标偏向格式记忆 | 训练 YAML 注释与超参设置 | 强调 JSON 约束、8 epoch、无 eval early-stop | 中等 |

## 5. 下一轮改进建议

### 5.1 先做推理侧快修

优先级 1：提高时序信息保留量

- 将推理采样帧数从 `8` 提升到 `24` 作为第一档，对照 `36` 做一次 ablation。
- 在不改权重的前提下先复测时间任务和联合任务，判断当前崩坏有多少来自采样不足。

优先级 2：收紧时间输出格式

- 时间字段只允许输出两种形式：
  - `{"time": "<float>s"}`
  - `{"time": null}`
- 推理 prompt 中显式禁止日期、帧序号、自然语言片段。
- 评测时对日期型字符串单独记为格式越界，而不是继续当“可解析时间”。

优先级 3：强化类型闭集约束

- 在 prompt 中直接给出允许标签集合，只允许输出以下闭集标签：
  `韧性断裂 / 脆性断裂 / 界面脱粘 / 齐根断裂 / 界面脱粘、齐根断裂 / 爆炸性断裂 / 半脆半韧断裂 / 未断裂 / 未夹紧 / 视频异常`
- 禁止输出 `颈缩断裂`、`撕裂`、`延性断裂`、`拉伸断裂` 之类标签外词。

优先级 4：保留 `null` 策略，但限定触发条件

- 仅在 `未断裂 / 未夹紧 / 视频异常 / 无法判断` 时允许输出 `null`。
- 对有明确 GT 时间的样本，应尽量避免默认回退到 `null`。

优先级 5：对齐训练与推理的系统指令

- 下一轮推理先使用与训练期一致的 system instruction 风格。
- 如条件允许，给 joint 任务增加 1-2 条 few-shot 样例，优先观察类型闭集是否变稳。

### 5.2 再做训练侧重训

优先级 1：把数据拆成清晰的三类子任务

- 单独构造 `time-only`、`type-only`、`joint` 三份训练集。
- 不再依赖同一批样本混合多种问法，让模型自己推断任务边界。

优先级 2：统一标签空间

- 类型标签全部标准化为中文闭集。
- 训练集里不再混入英文、同义词、错拼标签。

优先级 3：清洗异常样本

- 对 `未断裂 / 未夹紧 / 视频异常` 样本显式标记为异常类。
- 这类样本不要和正常断裂样本共用时间监督逻辑。

优先级 4：统一时间标注格式

- 时间字段统一成 `<float>s`。
- 清除多余空格、冒号时间、日期字符串等非目标格式。

优先级 5：增加验证集监控和 early-stop

- 下一轮训练必须打开 eval，不再只靠训练轮次和训练损失判断。
- 优先监控：
  - 时间任务：`parseable_rate`、`Hit@2s`
  - 类型任务：`Accuracy`、`Macro-F1`
  - 联合任务：`joint_success_rate`

优先级 6：改成分阶段训练

- 第一阶段：先让 joint 任务学会稳定输出闭集 JSON。
- 第二阶段：针对时间和类型分别做更聚焦的 task-specific 调优，避免三种任务相互干扰。

## 6. 下一轮实验计划

| 轮次 | 目标 | 只改这几项 | 验收重点 |
| --- | --- | --- | --- |
| Round 1 | 验证当前问题有多少来自推理侧 | 1) 8 帧改 24 帧 2) 闭集标签约束 3) 时间格式约束 | 时间可解析率是否明显回升；type collapse 是否缓解；联合成功是否从 0 提升 |
| Round 2 | 重建训练信号 | 1) 拆分三类训练集 2) 统一标签与时间格式 3) 加 eval + early-stop | 类型准确率是否脱离单类塌缩；时间是否不再集中在 `5-8s/null`；joint 成功率是否出现稳定正值 |

建议执行顺序：

1. 先做 Round 1，不改权重，快速验证推理侧是否能显著回收一部分能力。
2. 如果 Round 1 仍然没有明显起色，再进入 Round 2，避免把“推理错位”和“训练失败”混成一个问题。
